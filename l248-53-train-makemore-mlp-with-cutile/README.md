# 248 · Makemore: обучение MLP на GPU с cuTile

Продолжение [CPU-урока 247](../l247-52-generate-names-with-makemore-mlp/README.md): та же задача предсказания следующей буквы, обучение на NVIDIA GPU с помощью cuTile. Следующий [урок 249](../l249-54-makemore-batch-normalization/README.md) посвящён BatchNorm и работает на CPU.

## Запуск

Из папки этого урока:

```bash
cargo run
# Больше примеров на шаг и немного лучшее качество:
cargo run -- --batch 256 --steps 10000
# Короткий пробный запуск:
cargo run -- --steps 100
```

Из корня workspace:

```bash
cargo run -p l248-53-train-makemore-mlp-with-cutile
```

Зависимость `cutile = "0.4.0"` объявлена в `[workspace.dependencies]` и наследуется через `workspace = true`. Дополнительные features и переключатель `--gpu` не нужны. Код урока находится в `src/main.rs`: модуль `kernels` содержит GPU-ядра, остальные типы, константы и функции объявлены внутри `main`. Данные включены из `../l247-52-generate-names-with-makemore-mlp/data/names.txt`; интернет при запуске не нужен. Программа выводит метрики и 20 имён, выходные файлы не создаёт.

## Подготовка компьютера

Нужны Linux, Rust ≥ 1.89, совместимый NVIDIA-драйвер, CUDA Toolkit с `tileiras` и libclang для сборки `cuda-bindings`. На RTX 5070 Ti проверен Toolkit 13.2; полный `nvcc` для этих ядер не требуется. Для нестандартного расположения Toolkit задай `CUDA_TOOLKIT_PATH`. На Ubuntu системный libclang доступен в пакете `libclang-dev`. Требования для других GPU: [документация cuTile](https://nvidia.github.io/cuda-rust/cutile/latest/).

При пользовательской установке libclang пути можно один раз задать в локальном `~/.cargo/config.toml`, после чего также запускать только `cargo run`:

```toml
[env]
LIBCLANG_PATH = "/абсолютный/путь/к/библиотеке/libclang"
BINDGEN_EXTRA_CLANG_ARGS = "-isystem /абсолютный/путь/к/заголовкам/clang/include"
```

Это настройки конкретного компьютера; они не входят в репозиторий. На компьютере без NVIDIA запускай CPU-уроки 247 и 249 через `cargo run` в соответствующей папке. Они не зависят от cuTile. Команды с `--workspace` включают также GPU-урок и требуют его сборочных зависимостей; для CPU-проверок всего workspace используй `cargo test --workspace --exclude l248-53-train-makemore-mlp-with-cutile`.

## Что ускорено

Сохраняются задача предсказания следующей буквы, удаление копий имён перед split 80/10/10, обучаемые эмбеддинги, `tanh`, cross-entropy и ручной SGD. Этот урок использует embedding=8, first_layer_size=64, batch=128 и 10 000 шагов. `--batch` принимает кратные 32 значения от 32 до 4096; `--steps` — положительное число, кратное 10. Произведение steps × batch ограничено `i32::MAX`.

Вход дополняется нулями с 24 до 32 координат, словарь — с 27 до 32 столбцов. Пять дополнительных logits исключены из softmax; это не дополнительные символы. Матрицы умножаются тайлами 32 × 32 через `mma`, параметры и аккумуляторы имеют тип `f32`. Линейный слой объединён с `tanh`, его обратный проход — с производной `tanh`; softmax, loss и градиент logits считаются одним ядром. Градиенты эмбеддингов суммируют все повторные появления букв без гонок и атомиков.

Веса, данные, градиенты и промежуточные буферы остаются на GPU. CUDA Graph содержит 10 последовательных шагов, включая выбор новых примеров и обновление счётчика. Детерминированный unsigned hash счётчика задаёт выборку с возвращением; последовательность отличается от CPU `StdRng`. На каждом шаге память заново не выделяется, батч с CPU не копируется. На CPU возвращаются только редкие метрики. После обучения полные train/dev/test loss считаются на GPU; для последовательной генерации 20 имён веса один раз копируются на CPU.

Инициализация также изменена: `C ~ N(0,1)`, `W1 ~ N(0, (5/3)²/24)`, `W2 ~ N(0,0.01²)`, смещения нулевые. Это уменьшает начальное насыщение и позволяет сократить обучение. Learning rate = 0.3 на первых 75% шагов и 0.03 на оставшихся. Seed=42 фиксирует split и инициализацию, но не обещает побитового совпадения CPU и GPU.

## Как читать названия в коде

Параметры названы так же по смыслу, как в уроке 247: `character_embeddings`, `first_layer_weights`, `first_layer_biases`, `second_layer_weights`, `second_layer_biases`. Первый слой вычисляет `tanh(вход × W1 + b1)`, второй выдаёт оценки следующих символов. В GPU-варианте W2 хранится как `[FIRST_LAYER_SIZE, 32]`: сначала компонента первого слоя, затем индекс символа.

| Название | Что хранится или выполняется |
|---|---|
| `PADDED_CONTEXT_EMBEDDING_SIZE` | 32 входные координаты: 3 × 8 реальных и 8 нулевых |
| `FIRST_LAYER_SIZE` | 64 компонента первого слоя |
| `VOCABULARY_SIZE` | 27 настоящих символов; ещё 5 позиций GPU-буфера — дополнение |
| `TrainingConfiguration` | `batch_size` примеров на шаг, `training_steps` обновлений |
| `VocabularyCharacterIndexPairs` | Примеры в плоском массиве `[previous_0, previous_1, previous_2, target, ...]` |
| `ForwardAndBackwardBuffers` | Заранее выделенная GPU-память для промежуточных значений и производных |
| `context_embeddings_flattened` | Объединённые координаты трёх символов с дополнением до 32 |
| `first_layer_activations` | Результаты первого слоя после `tanh` |
| `next_character_scores_without_bias` | Произведение активаций на W2, ещё без прибавления b2 |
| `next_character_score_gradients` | `(вероятность − целевая метка) / batch_size` для каждого символа |
| `first_layer_pre_activation_gradients` | Производные по суммам первого слоя до `tanh` |
| `context_embeddings_flattened_gradients` | Производные по объединённым входным координатам |
| `negative_log_likelihood_losses` | Отдельный NLL каждого примера, ещё без усреднения |
| `record_forward_pass` | Записывает операции прямого прохода и softmax/NLL в CUDA Graph |
| `record_backward_pass` | Записывает вычисление всех градиентов параметров |
| `record_parameter_updates` | Записывает обновление параметров и увеличение счётчика шага |
| `build_training_graph` | Создаёт граф из десяти полных шагов обучения |
| `evaluate_mean_negative_log_likelihood` | Считает средний NLL набора без обновления весов |
| `generate_names` | Генерирует 20 имён на CPU с обученными параметрами |

В ядре `multiply_matrices` параметры `TRANSPOSE_LEFT_MATRIX` и `TRANSPOSE_RIGHT_MATRIX` задают транспонирование. Третий параметр, `MATRIX_OPERATION`, равен `0` для обычного произведения, `1` для прибавления смещений и `tanh`, `2` для умножения на производную `tanh`. В `.generics(...)` эти три настройки передаются в таком порядке строками, как требует cuTile. `tile_block_indexes` — координаты GPU-блока, а `shared_dimension_tile_index` — номер очередной части общей размерности матричного произведения.

`model_gradients` имеет ту же форму GPU-тензоров, что и `model`, но содержит производные, а не веса. GPU-ядра перезаписывают их на каждом шаге; старые значения не суммируются между шагами. В отличие от текущего CPU-урока, GPU-ядро `build_context_embedding_batch` по-прежнему выбирает примеры с возвращением с помощью хеша счётчика. Это переименование не меняет способ выборки или алгоритм обучения.

## Размеры компактной модели 8×64

Как и в уроке 247, полезная модель содержит 3571 обучаемый параметр.
Из-за выравнивания под GPU физические формы отличаются:

| Тензор | Полезная форма | GPU-буфер |
|---|---|---|
| C | [27, 8] | [32, 8] |
| W1 | [24, 64] | [32, 64] |
| b1 | [64] | [64] |
| W2 | [64, 27] | [64, 32] |
| b2 | [27] | [32] |

GPU-буферы параметров содержат 4448 чисел `f32`: 17 792 байта.
Вместе с такими же буферами градиентов — 35 584 байта (34.75 КиБ), без
активаций, датасета, CUDA Graph и служебных расходов CUDA. Полезные параметры
и градиенты без выравнивания заняли бы 28 568 байт, как в CPU-уроке.
Сборка батча и сбор градиентов используют эмбеддинги ширины 8; SGD обновляет
матрицы тайлами 8×8, GEMM по-прежнему использует 32×32. CPU-генерация учитывает
новую ширину эмбеддинга. Масштаб W1 рассчитан по 24 реальным входам.

Проверка 8×64 на RTX 5070 Ti: один полный запуск с batch=128 и 10 000
шагов дал dev NLL 3.291991 → 2.214319, test NLL 2.210480. Цикл обучения
занял 3.388 с, вся программа — 9.684 с (без Cargo-сборки). Это проверочный
прогон, не многократный бенчмарк скорости или качества.

## Замеры на RTX 5070 Ti

Исторические замеры модели embedding=16, first_layer_size=256.
Измерено 21 октября 2026 года, в таблице по одному прогону каждого режима, оптимизированный профиль урока. Время обучения не включает Cargo-сборку, подготовку/JIT, итоговую оценку и генерацию. Выбор GPU-настроек сделан по времени и dev loss.

| Режим | Батч | Шаги | Обучение | Dev loss |
|---|---:|---:|---:|---:|
| Исходный CPU | 32 | 200 000 | 93.8 с | 2.179930 |
| GPU, по умолчанию | 128 | 10 000 | 6.1 с | 2.133442 |
| GPU | 256 | 10 000 | 8.0 с | 2.122239 |
| GPU | 512 | 5 000 | 6.3 с | 2.143217 |

Для режима по умолчанию подготовка/JIT заняла около 5.2 с, вся программа — 11.8 с против 94.7 с у CPU. Это примерно 15× по времени обучения и 8× по всей программе **для этих режимов**. Сравнение включает изменение размеров модели, инициализации, батча и числа шагов; оно не измеряет ускорение одного и того же вычисления. Настройки выбраны среди проверенных вариантов, а не объявлены глобальным оптимумом. Повторный запуск режима по умолчанию дал то же качество за 5.4 с обучения и 11.0 с общего времени. Нагрузка на GPU и состояние JIT-кэша влияют на время.

После бенчмарка стандартный запуск изменён: копии удаляются до разделения

относятся к явно включаемому режиму `--benchmark-repeats`.

В `names.txt` 32 033 строки и 29 494 уникальных имени. 2 539 имён встречаются
ровно два раза, остальные — один. Удаление копий убирает 7.93% строк.
Для фиксированного split урока train содержит 182 790 символьных примеров
с копиями и 169 100 без них (−7.49%; GPU-буфер примеров: 2 924 640 →
2 705 600 байт). Это размер входных примеров, а не всей GPU-памяти.

Повторение сравнения на текущей архитектуре из корня workspace:

```bash
cargo build -p l248-53-train-makemore-mlp-with-cutile
python3 l248-53-train-makemore-mlp-with-cutile/benchmarks/duplicates.py
# Отдельный запуск без копий в train:
cargo run -p l248-53-train-makemore-mlp-with-cutile -- --model-seed 42
```

Обычный запуск использует только уникальные имена во всех трёх наборах;
`dev_loss`/`test_loss` теперь тоже считаются без копий. Дополнительный флаг
`--unique-train` для обычного запуска больше не нужен.
Для сравнения режимов скрипт явно включает `--benchmark-repeats`:
только в этом режиме dev/test сохраняют исходные частоты, печатаются также
`dev_unique_loss`/`test_unique_loss`, а `--unique-train` удаляет копии из train.
Все loss усредняются по символьным примерам, включая конец имени.
`--model-seed` меняет только инициализацию модели; split остаётся фиксированным
(seed=42). Без этого аргумента сохраняется прежняя последовательность
инициализации.

Методика: RTX 5070 Ti, cuTile 0.4.0, профиль `cargo build` с настройками
workspace, batch=128, 10 000 шагов, пять пар начальных весов (seed 42–46).
В каждой паре одинаковые split, начальные веса, learning rate и число
обновлений. Порядок режимов чередуется. GPU выбирает примеры с возвращением;
после изменения размера train последовательность выбранных примеров меняется.
Время включает только цикл обучения с синхронизацией и периодическими
метриками, исключает сборку, JIT, итоговую оценку и генерацию.
Исходные логи и CSV находятся в [benchmarks](benchmarks/).
SHA-256 датасета: `0a30b5557f192f32ab962680889aac5f6fda0f4cecf40a6d0b5694f58ea8cc4d`.

Результаты: среднее ± выборочное стандартное отклонение по пяти запускам.
Меньший NLL лучше; это разброс инициализаций на одном split, не доверительный
интервал по всем возможным датасетам.

| Train | Время, с | Dev NLL | Test NLL | Dev unique NLL | Test unique NLL |
|---|---:|---:|---:|---:|---:|
| С копиями | 5.664 ± 0.145 | 2.12914 ± 0.00316 | 2.12541 ± 0.00271 | 2.13390 ± 0.00329 | 2.12709 ± 0.00251 |
| Уникальные имена | 5.605 ± 0.128 | 2.13057 ± 0.00251 | 2.12581 ± 0.00224 | 2.13327 ± 0.00258 | 2.12584 ± 0.00221 |

Без копий среднее время уменьшилось на 1.05%, меньше разброса прогонов:
убедительного ускорения здесь нет. На исходном test изменение NLL +0.00040,
на уникальном test −0.00125. Практическая разница мала; результаты не доказывают
универсального преимущества одного режима. Для генератора уникальных имён
используется дедупликация по умолчанию: в этом эксперименте заметного ухудшения
нет. Если важны исходные частоты, сохраняйте кратности. Совпадение начального
dev loss и размеров проверочных наборов проверено во всех пяти парах.

Повторы задают веса: два экземпляра имени удваивают вклад его символьных
примеров в ожидаемый градиент относительно одного экземпляра. Если это
намеренные частоты наблюдений, удаление копий меняет задачу. Если нужны
равноправные уникальные имена, дедупликация соответствует этой цели.
Содержимое файла само по себе не доказывает, что кратность отражает
реальную популярность имён.

Хранить физические копии для сохранения частот необязательно: можно хранить
уникальные примеры и их кратности, выбирая примеры пропорционально кратности,
или точно учитывать кратности в нормированном полном loss. Простая равномерная
выборка из уникального набора этих весов не сохраняет. Такой взвешенный
режим здесь не реализован и не измерялся.

В этом уроке задано число шагов, а не эпох: меньше строк не означает меньше
вычислений на шаг. При обучении полными эпохами дедупликация сократила бы
число примеров за эпоху, но это уже другой бюджет обновлений. Продолжать
обучение после дедупликации математически можно, однако целевое распределение
изменится. Этот эксперимент сравнивает обучение с нуля; переключение из
сохранённого checkpoint не проверялось.

Для запуска также исправлены импорты внутри `kernels`: cuTile требует
доступных локальных типов/traits и корректно обрабатывает короткие имена
`Tensor`, `Tile`, `shape!` и операций. Формулы GPU-ядер сохранены.
